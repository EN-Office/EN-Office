# プロジェクト体制

## 役割とモデル割り当て

| 役割 | エージェント名 | モデル | 主な責務 |
|---|---|---|---|
| PM | （セッション本体） | Fable 5.1 | 全体管理、フェーズ設計、エージェントへの指示、成果物統合、ユーザーへの報告。必要時にタスクを自ら所有する |
| 企画 | `tgp-planner` | Opus | 支援スキーム・事業モデルの発想と構造化 |
| マーケティング | `tgp-marketing` | Sonnet | 顧客セグメント、集客チャネル、価格・課金モデル、ブランディング |
| 情報収集 | `tgp-researcher` | Sonnet | 業界構造、プロ制度、先行事例、市場規模、法規制の事実調査 |
| 実現性調査 | `tgp-feasibility` | Opus | 収益性・投資・法的リスク・運営負荷の採点、MVP提案 |
| 整合性確認 | `tgp-consistency` | Sonnet | 成果物間の矛盾・重複・抜け漏れ検出、用語統一 |
| 課題整理 | `tgp-issues` | Sonnet | 未決事項・リスク・ユーザー判断事項の抽出と優先度付け |

## 運営ルール
1. PMはフェーズごとに「問い」を定義し、必要な観点のエージェントへ並列に依頼する。
2. 各エージェントの成果物は `phases/` 配下にそのまま保存し、PMが統合版を作る。
3. 統合版は必ず `tgp-consistency` を通し、矛盾・重複を解消してから確定する。
4. 各フェーズ末に `tgp-issues` が課題リストを更新し、**ユーザー判断が必要な事項**を分離して報告する。
5. 事実と推測は常に区別する。数値には出典または「推測」を付ける。
6. フェーズ2以降、実現性の採点は `tgp-feasibility` が行い、企画担当は採点に関与しない（利害分離）。

## 呼び出し方
Claude Code セッション内で Agent ツールから `subagent_type: tgp-planner` のように指定する。
