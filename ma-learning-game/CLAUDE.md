作業前に必ず全文を読み、ここに書かれた規則に従ってください。

## 1. プロジェクト概要

- **目的**：M&A（企業の合併・買収）の取引プロセスを、ゲームを通じて体感的に学べるアプリを作る。
- **現フェーズ**：Phase 0「コンセプト・UX基礎設計」→ 次は Phase 1「モックアップ制作」。
- **最終成果物（当面）**：アプリのモックアップ（画面遷移が確認できるプロトタイプ）。
- **オーナー**：Yu（意思決定者。仕様の承認は必ず Yu が行う）
- **言語**：ドキュメント・UI文言・コミットメッセージはすべて日本語。M&A用語は初出時に英語を併記する（例：デューデリジェンス（Due Diligence, DD））。

## 4. 作業ルール（必須）

### 4.1 情報の正（Source of Truth）
- 情報の優先順位は **decisions（承認済みADR） > docs/03_spec > docs/02_ux > docs/01_concept > notes**。
- 矛盾を見つけたら、上位の情報に合わせて下位を直すか、`OPEN_QUESTIONS.md` に記載して Yu に確認する。勝手にどちらかを選ばない。

### 4.2 ドキュメントを変更するとき
- すべての正式ドキュメント（docs/ 配下）は冒頭にフロントマター（title / status / version / owner / updated / related）を持つ。変更時は `version` と `updated` を更新し、末尾の「変更履歴」に1行追記する。
- `status: approved` のドキュメントの**内容（仕様）**を変更する場合は、先に ADR を作成して Yu の承認を得る。誤字修正・リンク修正は ADR 不要。
- ファイルを `-v2` `_new` `_final` のように複製しない。履歴は git と変更履歴セクションで管理する。
- 廃止するドキュメントは削除せず `docs/99_archive/` に移動し、`status: deprecated` にする。

### 4.3 意思決定の記録
- 「やる／やらない」「AかBか」を選んだら、ADR を `decisions/` に作成し `DECISION_LOG.md` に1行追加する。
- Claude が作成した ADR は必ず `status: proposed` で始める。`accepted` に変えてよいのは Yu が承認した時だけ。

### 4.4 M&A情報の正確性
- M&Aの制度・用語・手法の説明は、学習アプリとして正確さが最重要。法令・会計基準・税務に関わる記述には出典（法令名、基準名、公的機関の資料など）を併記する。
- ゲーム上の簡略化を行う場合は、`learning-map.md` の「簡略化メモ」欄にどこをどう簡略化したかを書く（学習者を誤解させないため）。
- 実在企業を擬人化・モデル化しない（ケーススタディは公開情報に基づく匿名化・架空化を原則とする）。
- アプリ内の内容は投資助言・法的助言ではない旨の免責を仕様に含める。

### 4.5 機密・公開範囲
- このリポジトリには個人情報、取引先の非公開情報、実在案件の機密情報を書かない。
- APIキー等の秘密情報はコミットしない。

### 4.6 Git運用
- ブランチ：`feature/<内容>`、`docs/<内容>`、`fix/<内容>`。main へは PR 経由でマージする。
- コミットメッセージは日本語で「<種別>: <要約>」（種別：docs / feat / fix / chore / design）。
- 1つの PR では1つの目的だけを扱う。PR本文には「変更したドキュメント」「関連ADR」「Yuに確認してほしい点」を書く。
