# 情報管理規則

本プロジェクトで扱う情報（企画書、仕様書、意思決定、メモ、モックアップ）を、**人とClaude Codeの両方が迷わず扱える状態**に保つための規則です。

## 1. 基本原則

1. **一つの情報は一か所にだけ書く（Single Source of Truth）**。他の場所では内容を書き写さず、リンクで参照する。
2. **決まったことと、検討中のことを混ぜない**。決定は `decisions/`、検討中は `OPEN_QUESTIONS.md` と `notes/`。
3. **履歴を消さない**。上書きではなく、変更履歴とgitで追える形で更新する。
4. **承認者は Yu**。Claude（または他の作業者）は提案・起草までを行い、承認状態への変更は Yu の承認後に行う。

## 2. 情報の種類と置き場所

| 種類 | 置き場所 | 正式度 | 説明 |
|---|---|---|---|
| 作業指示 | `CLAUDE.md` | 正式 | Claude Code向けの作業ルール |
| 索引 | `README.md` | 正式 | 全ドキュメントへの入口 |
| 意思決定 | `decisions/ADR-*.md` | 最上位の正 | 何を・なぜ決めたか |
| 詳細仕様 | `docs/03_spec/` | 正式 | 画面・データ・ロジック |
| UX設計 | `docs/02_ux/` | 正式 | 体験設計、画面構成、進行 |
| コンセプト | `docs/01_concept/` | 正式 | 狙い、ターゲット、世界観 |
| 用語集 | `docs/glossary.md` | 正式 | M&A用語・ゲーム用語の唯一の定義 |
| 未決事項 | `OPEN_QUESTIONS.md` | 管理用 | 確認待ちの論点 |
| メモ | `notes/` | 非正式 | 議事録、調査、アイデア。ここに書いただけでは決定にならない |
| 廃止文書 | `docs/99_archive/` | 参照のみ | 過去の文書 |

**優先順位**：承認済みADR > 03_spec > 02_ux > 01_concept > notes
矛盾がある場合は上位を正とし、下位を修正する。判断がつかない場合は OPEN_QUESTIONS に記載する。

## 3. 命名規則

| 対象 | 規則 | 例 |
|---|---|---|
| ディレクトリ | `NN_英小文字` | `02_ux` |
| ドキュメント | 英小文字ケバブケース `.md` | `ux-foundation.md` |
| 画面仕様 | `screen-<画面ID>-<名前>.md` | `screen-S04-due-diligence.md` |
| ADR | `ADR-<4桁連番>-<ケバブケース>.md` | `ADR-0001-game-direction.md` |
| メモ | `YYYY-MM-DD-<内容>.md` | `2026-11-03-kickoff.md` |
| 画像等 | `docs/<分類>/assets/<ドキュメント名>-<連番>.png` | `ux-foundation-01.png` |

- ファイル名に日本語・スペース・`v2` `final` `new` などの版表記を入れない。
- 画面IDは `S01` から連番。採番は `docs/02_ux/ux-foundation.md` の画面一覧が正。

## 4. フロントマターとステータス

`docs/` 配下の正式ドキュメントは冒頭に以下を持つ。

```yaml
---
title: ドキュメント名
status: draft | review | approved | deprecated
version: 0.1
owner: Yu
updated: YYYY-MM-DD
related: [関連ファイルのパス]
---
```

### ステータスの流れ

```
draft（起草中）→ review（Yuの確認待ち）→ approved（承認済み）→ deprecated（廃止）
```

- `draft → review`：作成者が変更可能。
- `review → approved`：**Yu の承認時のみ**。承認はPRのApprove、またはスレッド上の明示的な承認発言をもって行い、そのPR番号/日付を変更履歴に残す。
- `approved` の文書の仕様変更は ADR を起票してから行う（後述）。

## 5. バージョン管理

- `version` は `メジャー.マイナー`。
  - マイナー（0.1 → 0.2）：追記・修正・表現変更。
  - メジャー（0.x → 1.0、1.x → 2.0）：承認、または方針が変わる変更。
- 各文書の末尾に「変更履歴」セクションを置き、`| 日付 | 版 | 変更内容 | 変更者 |` を1行ずつ追記する。
- 文書を複製して版を分けない（git履歴が正）。

## 6. 意思決定ログ（ADR）

### 6.1 ADRを書くべきとき
- ゲームの方向性、ターゲット、プラットフォーム、技術選定など、後から「なぜこうなった？」と聞かれそうなこと。
- `approved` の文書の仕様を変えるとき。
- 選択肢を比較して一つを選んだとき（選ばなかった案も残す）。

### 6.2 手順
1. `decisions/_template.md` をコピーして `ADR-<次の連番>-<内容>.md` を作る（status: proposed）。
2. `decisions/DECISION_LOG.md` に1行追加する。
3. Yu が承認したら status を `accepted` にし、日付と承認経路（PR番号など）を記録する。
4. 過去の決定を覆す場合は、新しいADRを作り、古いADRを `superseded by ADR-XXXX` にする（古いADRは削除しない）。

## 7. 仕様の更新手順

```
1. 変更の必要が生じる（Yuの指示 / 矛盾の発見 / 検証結果）
2. 影響範囲を確認（どの文書・画面IDに影響するか）
3. 仕様変更を伴う → ADRを起票（proposed）
4. 該当ドキュメントを更新（version・updated・変更履歴）
5. 関連する glossary / learning-map / 画面一覧 を同期
6. PRを作成し、PR本文に「変更文書」「関連ADR」「確認してほしい点」を記載
7. Yu の承認 → マージ → ADRを accepted に
```

## 8. 未決事項（OPEN_QUESTIONS）の扱い

- 書式：`| ID | 論点 | 選択肢/現時点の案 | 影響範囲 | 起票日 | 状態 |`
- IDは `Q-NNN` の連番。解決したら状態を `解決（ADR-XXXX）` とし、行は消さない。
- 確認待ちの論点を docs 本文に「TBD」で埋め込む場合、必ず Q-ID を併記する（例：`TBD（Q-003）`）。

## 9. M&A情報の正確性ルール

学習アプリである以上、誤った知識を教えることは最大のリスクとする。

1. 制度・法令・会計・税務の記述には出典を付ける（法令名と条文、会計基準名、公的機関資料等）。
2. ゲーム上の簡略化は `docs/02_ux/learning-map.md` の「簡略化メモ」に必ず記録する。
3. 用語の定義は `docs/glossary.md` が唯一の正。他文書で定義を書き直さない。
4. 法改正等で古くなる可能性がある情報には「確認日」を付ける。
5. 正式リリース前に、M&A実務の有識者による監修レビューを行う（OPEN_QUESTIONS Q-006）。

## 10. 機密・公開範囲

- 本リポジトリは公開されている可能性があるため、以下を書かない：個人情報、実在の未公表案件・取引先の非公開情報、社内情報、APIキー等の秘密情報。
- 実在企業を擬人化・キャラクター化しない。ケーススタディは公開情報を基にした架空企業で表現する。
- 他社ゲームの固有名・キャラクター・アートを模倣しない（参考にするのはジャンルやメカニクスまで）。

## 11. Claude Code の作業ルール（要約）

- 作業開始時：`CLAUDE.md` → 本規則 → `DECISION_LOG.md` → 対象文書の順に読む。
- 作業終了時：`CLAUDE.md` の「作業終了時のチェックリスト」を満たす。
- `accepted` のADRや `approved` の文書を、Yuの承認なしに書き換えない。
- 不明点は推測で埋めず `OPEN_QUESTIONS.md` に起票し、PR本文で Yu に確認を依頼する。
