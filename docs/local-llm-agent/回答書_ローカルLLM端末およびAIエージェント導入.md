### 2-3. 「16GB×2 で 32GB」の注意点（重要）

16GB×2枚は、**32GBのGPU 1枚と完全に同等ではありません**。

1. **分割方式の選択**
   - **llama.cpp（レイヤ分割）**：設定が簡単で安定しており、1ユーザ利用ではこれで十分です。ただし2枚は交互に動作するため、速度はほぼ1枚分です。
   - **vLLM（テンソル並列 TP=2）**：2枚が同時に計算するため高速になり、複数ユーザの同時利用にも強い方式です。同一型番の2枚が前提です。
2. **PCIe接続**：各GPUにCPU直結の **x8以上**を確保してください。チップセット経由（x4）の接続では、分割推論の性能が大きく落ちます。
3. **1枚あたりの上限**：モデルの重みとKVキャッシュ（会話履歴分のメモリ）を2枚に分けて載せるため、実効容量は32GBより少し小さくなります。目安は28〜30GBで見込んでください。
4. **同一型番で揃える**：vLLMのテンソル並列は、同一GPUの組み合わせが前提です。

### 2-4. VRAM 32GB でのモデル対応状況（2026年10月時点）

| モデル | 種別 | 4bit量子化時の目安VRAM | 32GBでの可否 | 用途の想定 |
|---|---|---|---|---|
| **Qwen3.6-27B** | dense 27B | 約18〜19GB（32Kコンテキスト）／約27GB（128K） | ◎ | コード解析・ログ解析。現時点で精度が最も高い候補です。 |
| **Qwen3.6-35B-A3B** | MoE（動作3B） | 約21GB | ◎ | 汎用・高速応答（Q&Aチャット）。生成が速いです。 |
| Qwen3-Coder-30B-A3B | MoE | 約19GB | ◎ | コーディングエージェント用途です。 |
| **gpt-oss-20b** | MoE | 約13〜16GB | ◎（1枚に収まります） | 軽量・高速。128Kのフルコンテキストが可能です。 |
| gpt-oss-120b | MoE | 約65GB | ✕（CPUオフロードが必要） | RAM 96〜128GBが必要なうえ速度が大きく落ちるため、本予算では非推奨です。 |
| 埋め込み・リランカー（bge-m3、Qwen3-Embedding 等） | 小型 | 1〜4GB | ◎ | RAG用。LLMと同居が可能です。 |

- **ライセンス**：Qwen3.6、gpt-oss はいずれも Apache 2.0 で、商用・社内利用が可能です。採用時は、念のため最新のモデルカードで確認してください。
- **日本語性能**：上記はいずれも日本語で実用水準にあります。業務用語（DoCAN、FG、アクティベーションコード 等）は、モデルの学習ではなく **RAG・用語集で補う**方針を推奨します。

### 2-5. 性能の目安

以下は公開ベンチマークおよびコミュニティ報告の値です。**当社環境での実測値ではありません**。導入後、フェーズ1で実測します。

| 構成 | モデル | 生成速度（目安） | 出典の種別 |
|---|---|---|---|
| RTX 5060 Ti 16GB ×1 | Qwen3 14B（Q4） | 約33 tok/s（16Kコンテキスト） | ベンチマークサイト計測 |
| RTX 5060 Ti 16GB ×1 | gpt-oss-20b | 128Kのフルコンテキストで動作 | ベンチマークサイト計測 |
| RTX 5060 Ti 16GB ×2（vLLM） | Qwen3.6-27B | 約50〜66 tok/s（204Kコンテキストで動作の報告あり） | 個人報告 |
| RTX 5070 Ti ×1 | Qwen3.6-35B-A3B | 約95〜130 tok/s | ガイド記事 |

- 人が読む速度は約10 tok/s です。**30 tok/s以上あればチャット用途で十分快適**です。
- エージェント用途では1タスクで数十回LLMを呼び出すため、速度が体感に直結します。**同時利用者は2〜3名程度まで**を想定してください。

## 3. 推奨構成（ソフトウェアアーキテクチャ）

貴社資料 p.2 の2台構成をそのまま採用できます。

```
[品川データ棟 11F 端末室（閉域）]
┌──────────── ローカルLLM用PC ───────────┐       ┌──────────────── 作業用PC ────────────────┐
│ Ubuntu 24.04 / NVIDIA Driver / CUDA      │       │ エージェント（OpenHands / Cline 等）       │
│ 推論サーバ：llama-server または vLLM     │◀─API─▶│ チャットUI（Open WebUI 等）                │
│  ・OpenAI互換API（社内LANのみ公開）      │ (LAN) │ RAG：埋め込み＋ベクトルDB（Qdrant/pgvector）│
│ モデル：Qwen3.6-27B / 35B-A3B 等         │       │ Tool/Skill：ログ取得・ソース検索・変換定義 │
│ 埋め込みモデル（同居可）                 │       │ 設定（プロンプト・用語集・権限）           │
└──────────────────────────────────────────┘       └──────────────┬───────────────────────────┘
                                                                     │（参照：読み取り専用から開始）
                                                       [FG開発環境：Apache / コンテンツ変換環境]
```

| レイヤ | 推奨ソフトウェア | 備考 |
|---|---|---|
| 推論サーバ | **llama.cpp（llama-server）**：導入容易、GGUF量子化 ／ **vLLM**：同時利用・高速 | フェーズ1は llama.cpp で開始し、必要に応じて vLLM に移行します。Ollama は手軽ですが、細かな制御には向きません。 |
| チャットUI | Open WebUI | ゴール1（Q&Aチャット）の画面として利用します。RAG機能も内蔵しています。 |
| RAG基盤 | Open WebUI内蔵RAG、または Dify（セルフホスト）／LlamaIndex | 小規模なら内蔵機能で開始し、高度化する場合は Dify 等に移行します。 |
| ベクトルDB | Qdrant ／ pgvector | **全文検索（BM25）とのハイブリッド検索**を推奨します（4-1参照）。 |
| エージェント | OpenHands ／ Cline・Roo Code（VS Code拡張）／ OpenAI互換API対応のCLIエージェント | いずれもローカルの OpenAI 互換 API に接続できます。 |
| 監視・ログ | 推論サーバのアクセスログ、プロンプト・応答ログ | 監査とチューニングに使用します。 |

### 閉域網ならではの導入ポイント

1. **オフライン搬入**：OSパッケージ、CUDA、Python wheel、Dockerイメージ、モデルファイル（数十GB）は、インターネット側で一括取得し、承認済み媒体で搬入します。**ハッシュ値の検証とウイルスチェック**の手順を事前に整備してください。
2. **テレメトリ無効化**：各OSSの外部通信（利用統計・自動更新）を無効化する設定を、手順書に明記します。
3. **バージョン固定**：更新のたびに搬入が必要になるため、動作確認済みのバージョン一式を「ベースライン」として管理します。
4. **アクセス制御**：推論APIは端末室LAN内のみに公開し、APIキーで認証します。

## 4. ローカルLLMを用いたAIエージェント導入について

### 4-1. ゴール別の実現方針

| ゴール | 方式 | 実現性 | ポイント |
|---|---|---|---|
| **ゴール1：過去Q&Aから回答案生成** | RAG（検索＋生成） | **高**：フェーズ1〜2で実用水準を狙えます。 | ・過去Q&Aの整形（1問1答化、日付・対象環境のメタデータ付与）が精度を左右します。<br>・「1127」「12345」のようなコード値は意味検索では外れやすいため、**キーワード検索を併用**します。<br>・回答には**根拠としたQ&Aの出典を必ず表示**し、人によるレビュー（Rv）を前提とします。 |
| **ゴール2a：コンテンツ変換の提案** | エージェント＋Tool（過去変換定義の検索、XML生成） | **中**：過去の変換定義の量と質に依存します。 | ・過去の `<pattern>` 定義をRAG化し、類似パターンを提示させます。<br>・**FGサーバへの反映（更新）は人が承認してから実行**します。 |
| **ゴール2b：ログ/ソース解析** | エージェント＋Tool（ログ取得、grep、ソース参照） | **中**：ログの前処理が鍵です。 | ・ログ全体をLLMに渡すとコンテキストを超えるため、**エラー行の周辺抽出などの前処理をToolで実施**します。<br>・スタックトレースから該当ソースの行を特定する処理は、ローカルLLMでも得意な領域です。 |

### 4-2. ローカルLLMの制約と対策

| 制約 | 内容 | 対策 |
|---|---|---|
| 精度 | クラウドの最上位モデル（ChatGPT／Codex 等）と比べると、推論力・長い手順の遂行力で劣ります。 | タスクを小さく分割し、Tool側で決定的な処理（検索・抽出）を担わせます。期待値を「サポート役」に設定します（貴社資料の想定どおりです）。 |
| ツール呼び出しの安定性 | 量子化の度合いにより、関数呼び出しの書式が崩れることがあります。 | 4bitは高品質な量子化（UD-Q4_K_XL 等）を選び、推奨サンプリング設定を適用します。フェーズ1で評価します。 |
| コンテキスト長 | 長くするほどVRAMを消費します。 | 32K〜64Kを標準とし、RAG・前処理で入力を絞ります。 |
| 同時利用 | 1台では2〜3名程度が上限です。 | 利用ルールを定めます。将来、利用者が増えたら台数を増やします。 |
| 学習（ファインチューニング） | 16GB×2では大規模な学習は困難です。 | **まずはRAG＋プロンプト＋Skill整備**で対応します。学習（LoRA等）は効果が見込める場合に限定して検討します。 |

### 4-3. 安全対策（エージェントの権限設計）

- **段階的な権限付与**：①参照のみ → ②提案のみ（差分表示）→ ③人の承認後に実行、の順に段階を上げます。
- FGサーバ・Apacheへの接続は、**読み取り専用アカウント**から開始します。
- エージェントのコマンド実行は**許可リスト方式**とし、破壊的な操作（削除・再起動 等）は禁止します。
- 全てのプロンプト・Tool実行を記録し、監査できる状態にします。
