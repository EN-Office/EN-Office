結論：既製のエージェントCLIを「接続先だけ」ローカルLLMに向ける

Claude Code／Codexのようなエージェントは、LLMをAPI経由で呼ぶ「操縦席」です。
APIの接続先を社内LANのローカルLLMサーバに差し替えれば、インターネットなしで動作します。

AClaude Code ＋ Gemma 4

Ollama が Anthropic Messages API 互換になったため、環境変数 ANTHROPIC_BASE_URL を差し替えるだけで接続できます。

操作感が最も良い。利用規約の確認が前提（p.9）。

BCodex CLI ＋ Gemma 4

--oss オプションや config.toml でローカルの Ollama を指定できます。

Apache-2.0 のOSS。閉域網へ持ち込みやすい。

COpenCode ＋ Gemma 4

OpenAI 互換APIを持つ任意のLLMを、設定ファイルで登録して使えます。

MIT ライセンスのOSS。マルチプロバイダ前提の設計。

推奨：フェーズ1では Codex CLI または OpenCode（OSS）を標準とし、Claude Code は規約確認後に比較評価の対象とします。
いずれも同じ LLM サーバ（Ollama ＋ Gemma 4）を共有できるため、エージェントは後から何度でも乗り換え可能です。

Gemma 4 の概要と、VRAM 32GB でのモデルの選び方

Google が 2026年4月に公開したオープンモデル。Apache 2.0 ライセンス、関数呼び出し（ツール利用）を標準サポート。

モデル（Ollamaタグ例）種別コンテキスト4bit時の目安32GBでの可否本PJでの用途
gemma4:31b-it-qatDense 31B256K約18〜20GB◎ログ／ソース解析など精度重視のエージェント
gemma4:26b-a4b-it-qatMoE（動作4B）256K約15〜17GB◎Q&Aチャットなど応答速度重視
gemma4:12b-it-qatDense 12B256K約8GB◎軽量タスク・要約・分類
gemma4:e4b ／ e2b小型128K約3〜5GB◎エージェント用途には力不足

コンテキスト長の設定が最重要

エージェントCLIは指示文・ツール定義だけで1〜2万トークンを使います。Ollama の既定値（数K）のままだと指示が切り捨てられ、動作が破綻します。最低32K、推奨64Kに設定してください。

比較候補も同じ手順で試せる

Qwen3.6-27B／35B-A3B、gpt-oss-20b も同じ Ollama で動作します。同一タスクで Gemma 4 と比較評価し、ツール呼び出しの安定性で選定します。

※ VRAM値はKVキャッシュを除く目安。公式モデルカード・Ollamaライブラリで要確認。4

Step 2-A：Claude Code を Gemma 4 に接続する

Ollama v0.14 以降は Anthropic Messages API（/v1/messages）互換。ツール呼び出し・ストリーミングにも対応しています。

作業用PC：環境変数を設定して起動（~/.bashrc 等）

# 接続先をローカルLLMサーバへ
export ANTHROPIC_BASE_URL="http://llm-pc:11434"
export ANTHROPIC_AUTH_TOKEN="ollama"   # ダミー値
export ANTHROPIC_API_KEY=""

# Claude Code が内部で使い分けるモデル階層を割り当て
export ANTHROPIC_DEFAULT_OPUS_MODEL="gemma4:31b-it-qat"
export ANTHROPIC_DEFAULT_SONNET_MODEL="gemma4:31b-it-qat"
export ANTHROPIC_DEFAULT_HAIKU_MODEL="gemma4:26b-a4b-it-qat"

# 閉域網向け：不要な外部通信を止める
export CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1

cd ~/work/fg-analysis
claude --model gemma4:31b-it-qat

搬入方法

インターネット側で npm pack @anthropic-ai/claude-code を実行して tgz を作成し、端末室で npm install -g ./xxx.tgz します。バージョンによってはネイティブバイナリ配布の場合もあるため、搬入するバージョンの手順に従ってください。

注意点

  • Claude Code は Anthropic の利用規約の下で提供されるソフトウェアで、他社モデルへの接続は公式サポート外の使い方です。
  • Claude 本体向けに最適化されているため、ローカルモデルではツール呼び出しの失敗が起きやすくなります。
参考：docs.ollama.com/api/anthropic-compatibility6

Step 2-B：Codex CLI を Gemma 4 に接続する

Codex CLI は Apache-2.0 のOSSで、ローカルLLM（Ollama 等）への接続を公式に想定しています。

簡易起動（同一PC上の Ollama を使う場合）

codex --oss -m gemma4:31b-it-qat

~/.codex/config.toml（LAN上のLLM用PCを使う場合）

model          = "gemma4:31b-it-qat"
model_provider = "llmpc"

[model_providers.llmpc]
name     = "Local LLM PC (Ollama)"
base_url = "http://llm-pc:11434/v1"

# 安全側の既定値：書き込みは作業ディレクトリ内のみ、
# コマンド実行は都度承認
sandbox_mode    = "workspace-write"
approval_policy = "on-request"

閉域網での利点

  • ライセンスが明快（Apache-2.0）で、社内審査を通しやすい
  • サンドボックス・承認ポリシーが標準装備で、「参照のみ → 承認後に実行」の段階導入と相性が良い
  • 指示書は AGENTS.md（OpenCode 等とも共通の形式）

搬入方法

npm pack @openai/codex の tgz、または GitHub Releases の単体バイナリを搬入します。

※ 設定キー（API方式の指定など）はバージョンで変わることがあります。搬入するバージョンの docs/config.md を同梱してください。

Step 2-C：OpenCode を Gemma 4 に接続する

OpenCode は MIT ライセンスのOSSエージェント。OpenAI 互換APIのモデルを設定ファイルで登録します。

プロジェクト直下の opencode.json

{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "llmpc": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Local LLM PC (Ollama)",

実装例②-1：最小エージェント（ツール定義）

エージェントの仕組みを理解するためのスキルトランスファー教材です（Python 約50行）。

import json, pathlib, subprocess
from openai import OpenAI  # 搬入: pip download openai

client = OpenAI(base_url="http://llm-pc:11434/v1",
                api_key="ollama")
MODEL = "gemma4:31b-it-qat"
LOGS = pathlib.Path("/mnt/fg-logs")
SRC  = pathlib.Path("/work/src").resolve()

def grep_log(pattern):
    r = subprocess.run(["grep", "-rn", "-C5", "--",
                        pattern, str(LOGS)],
                       capture_output=True, text=True,
                       timeout=30)
    return r.stdout[-8000:] or "該当なし"  # 量を制限

def read_source(path, start, end):
    p = (SRC / path).resolve()
    if SRC not in p.parents:          # 範囲外は拒否
        return "アクセス不可"
    lines = p.read_text(errors="replace").splitlines()
    return "\n".join(f"{i}: {l}" for i, l
                     in enumerate(lines[start-1:end], start))

FUNCS = {"grep_log": grep_log, "read_source": read_source}
def tool(name, desc, **props):
    return {"type": "function", "function": {
        "name": name, "description": desc,
        "parameters": {"type": "object", "properties": props,
                       "required": list(props)}}}

TOOLS = [
  tool("grep_log", "Amacheログを正規表現で検索",
       pattern={"type": "string"}),
  tool("read_source", "ソースの指定行範囲を読む",
       path={"type": "string"},
       start={"type": "integer"}, end={"type": "integer"}),
]

ツール設計の3原則

  • 読み取り専用：書き込み系の関数は作らない
  • 出力量の制限：末尾8,000文字までに絞る
  • パスの制限：ソース置き場の外は読ませない

実装例②-2：最小エージェント（エージェントループ）

LLMがツール呼び出しを要求する限り実行と返却を繰り返し、要求がなくなったら最終回答とします。

def run(question, max_steps=10):
    msgs = [{"role": "system", "content":
             "FGサーバ不具合の解析支援。被疑箇所を ファイル:行 で示す。"},
            {"role": "user", "content": question}]
    for _ in range(max_steps):
        msg = client.chat.completions.create(
            model=MODEL, messages=msgs, tools=TOOLS).choices[0].message
        msgs.append(msg)
        if not msg.tool_calls:           # 最終回答
            return msg.content
        for c in msg.tool_calls:         # ツール実行
            out = FUNCS[c.function.name](
                **json.loads(c.function.arguments))
            msgs.append({"role": "tool",
                         "tool_call_id": c.id, "content": out})

print(run("10:15頃からFGのレスポンスが返らない"))

動作の流れ

  1. 質問とツール一覧を Gemma 4 に送る
  2. Gemma 4 が grep_log("Exception") を要求
  3. Python が実行し、結果をそのまま返す
  4. Gemma 4 が read_source("…/Hoge.java", 1, 62) を要求
  5. ツール要求がなくなったら最終回答を出力

ローカルLLMでエージェントを安定させるコツ

クラウドの最上位モデルより推論力が劣る前提で、「LLMに考えさせる量」を減らす設計にします。

うまくいかない典型例と対策

症状対策
指示を無視する／途中で止まるコンテキスト長が不足しています。64Kに設定してください。
ツール呼び出しの書式が崩れる量子化を上げる（QAT版・Q5以上）か、31B に切り替えます。
ログを丸ごと読んで溢れるツール側で出力を制限します（例：末尾8,000文字まで）。
同じ操作を繰り返す最大ステップ数を設定し、手順を指示書に明記します。
応答が遅い軽いタスクは 26B-A4B に振り分けます。

設計の原則

  • 決定的な処理はツールへ：検索・抽出・整形はスクリプトで行い、LLMは判断と説明に専念させる
  • タスクを小さく：「原因を特定して直す」ではなく「被疑箇所を3つ挙げる」
  • 手順を指示書に書く：熟練者の調査手順を AGENTS.md に落とし込む
  • 評価セットを作る：過去の障害10件程度で、モデル・設定変更の効果を測る

性能の目安（RTX 5060 Ti ×2）

同時利用は2〜3名程度まで。エージェントは1タスクで数十回LLMを呼ぶため、1件あたり数分を想定します（実測はフェーズ1で実施）。
